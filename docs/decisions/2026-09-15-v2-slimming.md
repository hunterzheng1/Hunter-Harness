# v1.0 瘦身重构决策记录

日期：2026-09-15 决策，2026-09-16 实施完成
状态：已随 1.0.0 落地（破坏性升级，无向后兼容）

本文档记录 0.x → 1.0.0 破坏性瘦身的 13 条决策，每条含背景、决策与后果。服务端配套硬切割计划见 `hunter-platform/.zcode/plans/`（本仓库不含服务端代码）。

## D1 移除安装时 agent 选择

- 背景：0.x 安装需用户在 5 个 agent（claude-code/codex/cursor/codebuddy/pi）中选择，适配器矩阵维护成本高，且多数团队只用一种规范投影。
- 决策：安装零选择，技能固定投影到 `.agents/skills/`（AGENTS.md 生态的规范面）。
- 后果：删除 `--agents` 参数、交互菜单与适配器矩阵；`.claude/skills`、`.cursor`、` .pi` 投影面退役。

## D2 CodeBuddy 无条件双写

- 背景：CodeBuddy 是主要使用环境，但其技能目录为 `.codebuddy/skills/`。
- 决策：`.agents/skills/` 为规范投影，`.codebuddy/skills/` 无条件派生双写（内容一致），无需任何开关。
- 后果：投影逻辑固定为"1 规范 + 1 派生"；双写不覆盖 CodeBuddy 的 rules 目录（静态 rules 已删，见 D5）。

## D3 移除 Installation Profile（general/java）

- 背景：profile 维度（general/java）为早期多语言设想，实际 java overlay 长期无人使用，却让 schema、数据管线、CLI 全链多带一个维度。
- 决策：profile 概念整体删除，只保留唯一通用内容集。
- 后果：删除 `overlays/java`、数据包 java bundles/manifests、schema 枚举、`adapt-agent-bundle.mjs`；`sync-harness.mjs` 改单 bundle 生成；安装/更新/refresh 不再透传 profile。

## D4 指令文件收敛为 AGENTS.md 单文件

- 背景：0.x 同时维护 AGENTS.md / CLAUDE.md / CODEBUDDY.md 三个受管块；CodeBuddy 官方行为是无 CODEBUDDY.md 时自动加载 AGENTS.md，两者并存时 CODEBUDDY.md 反而屏蔽 AGENTS.md。
- 决策：只保留 AGENTS.md 一个受管块；CLAUDE.md / CODEBUDDY.md 受管块及其投影全部删除。
- 后果：指令维护面从 3 收敛到 1；`sync` 不再生成 CLAUDE.md；uninstall 负责清理历史块（D9）。

## D5 删除静态 rules 文件投影

- 背景：`.harness/rules/project-guidance.md` 及 java 变体是静态模板，内容很快过期，且与归档学习出的经验规则职责重叠。
- 决策：静态 rules 文件全删；规则改由归档自动学习维护（D6）。
- 后果：`.harness/rules/`、`.claude/rules/` 不再是受管路径；push 扫描集不含 rules。

## D6 规则候选自动化（取消人工评审队列）

- 背景：0.x 的规则候选进入 rules-review 人工队列，实际评审率极低，候选堆积。
- 决策：`archive upload` finalize 后自动执行规则候选提取（注入过滤 + 置信分级不变），高置信候选幂等刷新进 AGENTS.md 独立"经验规则"受管段（与手写内容隔离）。
- 后果：删除 CLI `rules-review` 命令、core proposals 中 rule_candidates 人工环节；AGENTS.md 新增一个可幂等刷新的受管段。

## D7 sync 体检瘦身

- 背景：sync 体检中 knowledge/rules 两个组件不做实际检查（伪组件），CLAUDE.md 生成随 D4 失效。
- 决策：删除 knowledge/rules 伪组件；instruction-graph 组件入口只剩 AGENTS.md。
- 后果：体检输出只剩真实检查的组件；报告结构不变。

## D8 删除提案流与零使用回执

- 背景：instructions audit/apply 提案流（core/src/proposal）、rules-sync 兼容壳、知识 asset-receipts 回执（harness_assets.py）均为零使用死链路。
- 决策：硬删除三整条链路及对应 CLI 命令（`instructions`、`rules-sync`）。
- 后果：服务端配套退役同名接口（见 hunter-platform 计划文档）；contracts 删 rules scope 与 rule contentKind。

## D9 新增 uninstall 命令

- 背景：硬切割（D10）要求用户能干净地清除 0.x 历史投影，手工删除既危险又繁琐。
- 决策：新增 `hunter-harness uninstall`：按 manifest + 历史适配器根清单精确删除所有历史版本写入的内容（`.agents`/`.claude`/`.cursor`/`.pi`/`.codebuddy` 受管文件、AGENTS.md/CLAUDE.md/CODEBUDDY.md 受管段落、`.mcp.json` harness 条目、`.harness/`）；默认 dry-run，`--yes` 执行，`--keep-data` 保留运行数据，`--global` 清理用户级目录。
- 后果：用户手写内容零风险；旧项目迁移路径 = uninstall → init。

## D10 硬切割，不做兼容过渡

- 背景（用户确认）：不考虑存量项目平滑迁移。
- 决策：新旧 CLI/数据包互不兼容，靠 family 清单 `minimumCliVersion` + `bundle_version` 门禁互相拒绝；服务端接口硬删，不做 410 Gone 过渡；contracts 直接删 rules scope 与 rule contentKind。
- 后果：0.x 项目必须 uninstall 后重新 init；服务端随 1.0.0 同步硬删（计划文档先行）。

## D11 旧配置软着陆（仅配置文件）

- 背景：D10 硬切割之外，用户手写的 `.harness/project.yaml` / init config 里可能残留废弃字段，直接 schema 报错体验差。
- 决策：`stripLegacyConfigFields()` 在 strict parse 前剥离废弃字段（agents/profile/surface 等）并打印 deprecation warning；init/refresh 检测到 0.x 投影残留时打 warning 引导 uninstall（不自动删）。
- 后果：配置文件层面不炸；投影面层面不妥协。

## D12 skill-cli install 固定双写，upload 保留 --agent

- 背景：skill-cli 0.x 的 install 支持 `--agent claude-code/cursor/...` 多面安装，与 D1/D2 矛盾；但 upload 是把草稿推给服务端的具体适配器通道，服务端仍按适配器构建工件。
- 决策：`INSTALLABLE_AGENTS = {codex, codebuddy}`：install 无 `--agent` 时固定双写两面，`--agent` 只能收窄到这两面之一（其他值 exit 3）；upload 的 `--agent`（claude-code/codex/cursor）保留不动。
- 后果：install 不再询问 agent（TTY 仅询问 scope 与确认）；`.claude/skills` 等历史安装面由 uninstall 清理。

## D13 版本四点同步与数据包拍平

- 背景：0.x 的 family.json 嵌套结构与 bundle 目录层级随单 bundle（D3）失去意义。
- 决策：发布时四点同提交改齐 1.0.0——`packages/cli/package.json`、`packages/workflow-data-harness/package.json`、`hunter-workflow-family.json`（`bundle_version` + `workflowPackageVersion` + `minimumCliVersion`）、`scripts/sync-harness.mjs` 的版本常量；数据包目录拍平，family.json 更名 `hunter-workflow-family.json`；孤儿迁移文件（resources/harness/migrations）删除。
- 后果：版本不一致会被 sync 自校验与 release:preflight 拦截；tag/publish 由维护者按 SOP 另行执行。
