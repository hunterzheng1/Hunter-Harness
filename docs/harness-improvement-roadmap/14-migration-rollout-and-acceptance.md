# 阶段 14：迁移、发布与整体验收

## 目标

在不破坏已有项目、归档、基线和 Skill 调用方式的前提下，分批启用新同步与知识模型，并建立可观测的回滚点。

## 依赖与并行边界

本阶段是唯一整合阶段，依赖 01～13 对应工作包全部达到关闭条件，不与尚未完成的功能 Implementation 并行关闭。迁移脚本、功能开关、数据回填和真实流程可以分别开发，但必须按同一迁移矩阵和发布候选汇合。

每次迁移记录：旧版本、目标版本、批次游标、成功/失败数量、可重试原因和回滚能力。迁移必须可断点续跑；页面切换不能作为数据迁移成功的唯一证据。

## 迁移矩阵

| 旧状态 | 目标状态 | 兼容读取 | 删除旧写入的条件 |
|---|---|---|---|
| 项目级最新快照 | 按分支不可变快照 | 旧数据归入“未标记分支” | 新 Push/Pull 和恢复流程稳定 |
| 单一 `knowledge_status` | 四个拆分状态 | 服务端双读并推导展示 | 历史记录完成回填 |
| core-v1 归档包 | core-v2 结构化摘要、证明与两类候选 | 服务端兼容投影旧 `summary-data.json` | 新客户端只写 core-v2，历史包补处理验证完成 |
| ZIP 路径混在本地归档收据 | `LocalArchiveReceipt`、`ArchivePackageReceipt` 和 outbox 分离 | 兼容 Adapter 从旧回执派生包身份并重新验哈希 | 所有待重试包完成迁移或明确丢弃 |
| Codebase Map 旧 manifest | `MapManifestV2` | Map Reader 双读 | 旧项目至少成功发布一次 v2 |
| `project-guidance.md` 与旧 Agent 投影 | 多文件 canonical 规则和 Adapter 收据 | 转换为待审提案，保留用户修改 | 冲突已处理且新投影验证通过 |
| 顺序执行且普通模式可写的旧 Sync | Provider 计划、选择性应用和局部复查 | 保留 `--check`、`--dry-run`、`--apply safe` 和 `--fix` 输入，转换为新计划语义 | 默认零写入、动作迁移和第二次无变化运行通过验收 |
| 手动 `harness-knowledge-ingest` | 归档后服务端自动提取 | 兼容入口查询或触发同一队列 | 历史补处理和页面重试稳定 |
| 旧复杂度与阶段字段 | `PlanProfile` | 明确映射旧字段 | 所有下游读取新 schema |
| 旧 Plan 文档与事件 | 新职责产物和机器事件 | finalizer 与页面兼容读取 | Run～Archive 及 Platform 验证完成 |

## 迁移顺序

### 1. 契约与双读

- 先发布向后兼容的 OpenAPI 和存储字段。
- 服务端能读取旧项目级快照与新分支快照。
- 旧项目级快照归入“未标记分支”。
- 状态字段从单一 `knowledge_status` 双读到拆分状态。

### 2. Core 与兼容命令

- 启用统一 `RemoteSyncModule`。
- 新增 Push/Pull，但保留 `update` 和必要旧命令的兼容入口。
- 旧调用产生清晰弃用提示，不立即失败。

### 3. Codebase Map 与规则治理切换

- Map manifest 双读旧格式和 v2，新写入只使用 v2。
- 旧 `project-guidance.md` 转换为待审规则提案，不自动拆分并覆盖 canonical 文件。
- Agent 旧投影先识别本地修改，再生成新 Adapter 投影。
- `rules-sync` 保留为带弃用提示的兼容入口。

### 4. Sync 与 Archive 切换

- 先让 Sync 使用只读 Provider 和真实收据，普通模式不再隐式刷新 Adapter。
- 再启用带预览哈希的选择性应用、局部复查和统一上传询问。
- 迁移时保留每个 Agent 的既有 Profile；未选择 Profile 迁移动作时不得统一覆盖。
- 持久保存 CodeGraph 等功能开关；旧项目缺少开关时采用兼容推导并记录来源，不能把未配置误报为检查失败。
- 删除固定 `knowledge` 收据、`knowledge-sync` 能力要求和每次固定出现的规则审计提示。
- 确认已发布包和外部调用均不依赖后，再删除旧 `harness_sync.py`、重复 CodeGraph 探测函数和相关打包清单项。
- 同步更新当前 Skill、reference 和 CLI 使用说明；历史 Changelog 保留原行为说明，不回写历史。
- Archive 改用 Core 上传，并先同步本地终态。
- 本地归档、核心包和远端耐久收据分开迁移；旧待上传 ZIP 在加入 outbox 前重新校验包哈希和项目身份。
- 监控确认不再把网络上传时间计入归档阶段。

### 5. 知识自动化

- 为新归档自动提取。
- 后台按批次补处理历史归档。
- 使用提取器和索引 Schema 版本重建旧分类。
- 观察稳定后再隐藏并移除用户侧 Ingest Skill。

### 6. 非监控页面兼容切换

- 先上线分支文件和项目资料。
- 再收敛项目知识与变更记录。
- 保留旧监控和短期旧页面只读入口，不提前依赖新 Plan 事件。

### 7. Plan 协议切换

- 先发布新的 `PlanProfile`、`PlanningContext` 和产物字段的兼容读取。
- 再让新版本写入新字段，并启用决策前沿和精简审批。
- 随后启用产物派生、语义一致性检查和事件精简。
- 旧 frontmatter、现有六项标准输入和旧 `implementation-detail.md` 继续可读。
- Run、Test、Review、Submit、Archive 和 Platform 逐项验证后，才移除旧写入逻辑。

### 8. 监控与旧入口收尾

- Platform 监控切换到阶段 12 的机器事件 Schema。
- 对比新旧页面数量、状态和版本来源。
- 确认数据一致后删除旧页面、旧写入和弃用入口；兼容读取按迁移矩阵保留。

## Plan 专项基线

在阶段 08 开始前记录可获得的基线；没有可靠数据的指标标记为「待采集」，不得补造数值：

- Plan 总耗时和用户阻塞交互轮数。
- 澄清问题和远端知识查询次数。
- CodeGraph、Codebase Map 和文件读取次数。
- 规划产物总字数和重复段落数量。
- `finalize` 首次成功率及阶段交接重试次数。
- 语义检查发现的问题和用户审批后重新纠正范围的次数。

## 必测场景

### Push/Pull 同步

- 配置包含账号、URL、`token` 字段名，但不包含凭据文件路径。
- 本地文件缺失、远端存在，Pull 可恢复。
- 本地与远端同时变化，必须冲突确认。
- 两个客户端并发 Push，不产生空版本、重复版本或未经确认的内容。
- 远端版本前进后本地差异归零，正确刷新基线并返回无变化。

### Sync 本地维护

- 默认运行、`--check` 和只生成计划均不写文件。
- `--apply safe` 只应用低风险且不需要额外确认的动作；`--fix <id>` 不执行无关动作。
- 用户取消、目标文件变化或计划过期时，不执行旧计划。
- 两个 Agent 使用不同 Profile 时，检查和无关修复保持原配置。
- Adapter 应用后重新读取版本与内容哈希，收据准确记录实际写入和验证结果。
- 没有活动 Change 时不解析 Python；Python 不可用不阻塞其他只读 Provider。
- 未启用 Map、CodeGraph、规则或配置来源时返回不适用，不产生全局 WARN。
- Windows npm 启动器可以安全执行 CodeGraph 状态命令；权威状态不可用时不根据递归扫描宣称索引最新。
- 单个 Provider 超时、返回无效结果或抛出异常时，其他组件继续完成，最终摘要保留全部结果。
- 输入未变化的第二次运行不刷新 Adapter、不重建 Map、不生成规则提案，也不询问上传。
- 应用多个本地动作后只出现一次上传确认，并复用同一 `RemoteSyncModule`。

### Codebase Map 与规则

- 旧 Map manifest 可读；首次 v2 刷新原子发布，失败不污染旧地图。
- 无相关输入变化时不调用 Mapper 或规则提案模型。
- `CONVENTIONS.md` 观察项不会未经审阅成为 canonical 规则。
- 旧 `project-guidance.md`、用户修改过的 Agent 投影和新多文件规则迁移不丢内容。
- 架构事实、架构约束和 ADR 在存储与页面中保持不同类型。

### 归档与知识

- `completed`、`abandoned`、`superseded` 与 `release-candidate`、`record-only` 的关闭矩阵服从 `PlannedPhaseSet.planned_phases`。
- 无 Git、无 upstream、没有 Submit 以及主动提前结束的 Change 能按策略形成 record-only 归档，不补造未计划阶段证据。
- 在 staging、manifest、本地原子发布、包构建、outbox 和远端回执各点中断后，resume/reconcile 保持幂等。
- 默认归档路径的全树读取次数、重复哈希次数和 ZIP 构建次数满足阶段 06 预算；相同输入重试复用已有内容清单和包。
- Archive、Push 和 Sync 不启动嵌套 `npx` 复用其他入口。
- ZIP 上传成功、知识提取失败：归档仍可下载，任务可重试。
- 收到匹配的远端耐久收据后可清理本地重试 ZIP；知识失败不会要求客户端保留或重传同包。
- 同一 ZIP 重传：不重复生成知识。
- 历史归档补处理：只新增缺失知识或升级旧提取版本。
- Query 只返回知识类型，不返回设计、计划、规则和架构。
- 本地原子发布后的终态同步先于所有后置服务停止、包上传和项目内容 Push；步骤开始前为冻结输入执行的单次 `quiesce` 不属于后置停止。

### Platform

- 多分支能看到各自最近快照。
- 未标记旧数据不会被错误标成主分支。
- 项目资料和项目知识无重复条目。
- 大量变更记录、文件和项目时，接口分页且并发有界。
- 变更记录首页按最新稳定顺序返回；“导出全部”沿游标读取完整授权结果，不只导出已加载页。
- 跨租户全局搜索和 MCP 查询不会泄露其他项目。

### Plan

- 简单修复最多一次澄清、一次默认知识查询和一次结构化探索，不执行无必要的对抗评审。
- 常规功能将互不依赖的问题放在同一轮，并验证 design、plan 和 scenarios 的语义一致性。
- 高风险功能按依赖处理决策，并覆盖适用的安全、迁移、并发、幂等和失败恢复要求。
- 远端不可用时只记录一次知识查询失败，不建立本地索引或重复执行 Sync/Query。
- 用户中途纠正范围时，旧意图和受影响证据失效，必要时重新分类 `PlanProfile`。
- 中断恢复不重复已确认决策、稳定知识查询和代码探索；finalizer 重试保持幂等。
- 旧格式变更目录仍能被读取、验证并交接给下游阶段。

## 发布指标

建议至少观察：

- Push/Pull 平均耗时、P95 和无变化快速返回比例。
- 冲突数量及用户取消比例。
- 归档 ZIP 上传成功率和待重试数量。
- 本地归档 P50/P95、文件数、输入字节、全树读取次数、ZIP 构建时间和分步骤耗时。
- 知识提取队列长度、失败率、平均条目数和重复合并率。
- Sync 每次实际执行动作数、无变化动作跳过率和平均耗时。
- Sync 各 Provider 的适用率、跳过率、超时率和失败隔离结果。
- Sync 默认检查和应用模式的耗时分布，以及第二次无变化运行相对首次运行的耗时变化。
- Codebase Map 增量命中率、完整重建比例和每次消费的证据预算。
- 规则检查跳过率、提案采纳率、投影冲突数和始终加载上下文大小。
- Platform 页面首屏耗时、分页请求数和搜索错误率。
- Plan 总耗时、阻塞交互轮数和远端查询次数。
- Plan 产物体积、重复内容比例和 `finalize` 首次成功率。
- 语义检查有效发现率、误报率和风险重新分类次数。

## 回滚策略

- 新旧读取路径在迁移期并存；写入切换使用功能开关。
- 新知识索引使用独立 Schema 版本，回滚不删除旧归档或 Blob。
- 任何阶段失败时可停用新入口，但不能回滚已经持久保存的用户文件版本。
- 移除旧 Skill、字段或页面前，至少完成一个稳定发布周期和历史数据校验。
- Plan 读取兼容保留时间长于写入兼容；回退 Agent 指令时，不回退已经发布且向后兼容的机器 Schema。
- 新语义检查误报过高时先降为建议，不关闭确定性结构门。
- 新审批交互在特定宿主不可用时只回退展示方式，不回退决策树状态模型。

## 验收条件

- 用户能够明确选择上传范围并预览差异。
- 本地关键文件误删后可以从指定分支恢复。
- 配置不会因内容敏感词误报，但凭据始终不上传。
- Sync 不再管理知识，也不重复执行无变化检查。
- Sync 默认只读，所有写入都能关联到用户选择、预览哈希、实际收据和写入后验证。
- Sync 保留每个 Agent 的 Profile；可选功能未启用时不会产生虚假警告。
- Sync 的 Python、CodeGraph 和其他外部依赖按 Provider 延迟解析，单项失败不会丢失整次检查结果。
- Codebase Map 只在证据变化时刷新，规则治理只消费按主题选择的事实。
- canonical 规则、Agent 投影、架构地图和 ADR 的归属清晰且可追溯。
- 归档自动上传 ZIP，并由服务端异步提取知识。
- 项目知识只包含可复用知识；规则、架构、指令、配置和变更资料分别展示。
- 所有旧项目均能平滑读取和自然迁移，无需用户清空状态。
- Plan 不再重复分类、确认阶段计划或生成叙述式自检。
- Plan 的独立问题可同轮处理，远端知识查询有明确预算。
- design、plan 和 scenarios 职责清晰，中高风险语义遗漏能在编码前发现。
- 高风险保护、原子 finalizer、机器审计证据和下游兼容没有退化。

## 非目标

- 不在本阶段重新设计阶段 01～13 已冻结的 Interface。
- 不以删除旧数据、清空项目状态或重建所有归档作为迁移前提。
- 不用页面显示正常替代存储回填、兼容读取和真实收据验证。
- 不把无关全仓长测试设为每个迁移小提交的默认门禁；最终候选仍执行完整发布策略。

## 发布门

1. 各阶段聚焦测试和受影响模块回归通过。
2. Harness、CLI、Server 和 Web 的契约测试按实际改动面选择，不把无关全仓长测试作为每个小阶段的默认要求。
3. 与 Platform 相关的 OpenAPI 在两个仓库中保持一致。
4. 使用新项目和旧格式项目分别完成一条真实流程。
5. 验证分支快照、Pull 恢复、归档 ZIP、知识提取、Plan 产物、事件和页面展示。
6. 最终候选仍执行发布策略规定的候选验证。
7. 路线目录受 Git 跟踪；跨文档契约注册表、OpenAPI、生成类型和消费方使用相同版本，文档链接与必需章节校验通过。
