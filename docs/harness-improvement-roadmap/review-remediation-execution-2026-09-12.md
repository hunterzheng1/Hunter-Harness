## 3. 实施原则与边界

- 首先确认实际代码状态，已被修复的项目核验后登记证据，不重复修改。
- 先为缺陷建立能失败的行为回归，再修复。不能用放宽门禁、伪造收据、跳过测试或重命名状态掩盖问题。
- 确定唯一提交范围、风险来源、证据来源和任务写入权威。自动化减少模型记账，不能增加隐含权限。
- 小任务保留低成本正常路径；不要为每次编辑新增通用工作流框架、数据库或常驻服务。
- 根据文件或真实依赖变化使证据失效；相关输入改变时不能为节省时间继续复用。
- 不通过整仓清理、硬重置、覆盖用户变更、强推或删除未核验文件推进任务。
- 大型多阶段实施使用隔离分支或工作树。按仓库规则验证、合并与推送；npm 发布、部署和对外共享遵守实际授权，不从任务书推定额外权限。
- Hunter Platform 相关变化先核验该仓库代码、规则和消费者。若实施范围涉及两仓，记录两仓提交与兼容证据，不只交付本地 mock。
- 普通技术选择自主解决；只有业务歧义、授权缺口或外部条件确实阻塞时提问，继续不依赖该问题的工作。

## 4. R1：完整候选范围参与风险判定

**目标：** 无论首次 finish、验证失败后重试还是恢复，实际将被提交的产品改动都参与风险判断。

实施要求：

1. 在风险分类前解析完整候选改动，包括新增、修改、删除、重命名、暂存和未暂存内容。
2. 区分本任务修改、用户既有修改和其他任务修改。不能把所有新出现的 foreign 文件自动当成验证副作用并纳入提交。
3. 范围确定后重新计算风险与所需验证；full 信号必须在执行提交前生效。不能只更新 ownership 而沿用旧 tier。
4. 验证后、提交前复核候选内容；并发写入或测试副作用改变产品内容时重新判定，或返回明确冲突。
5. 使用精确提交范围，防止 `git add -A` 越界吸纳文件；不破坏用户原有暂存状态。

必测：原 README 失败重试后新增权限文件；新增迁移或契约配置；重命名跨风险边界；混入他人文件；验证过程修改产品文件；合法测试输出不错误升级或被提交。高风险反例不得以 fast 完成或生成产品提交。

## 5. R2：取消与取代任务不隐式提交

**目标：** `abandoned`、`superseded` 等非成功闭包只记录对应结果，不自动提交未验证产品修改。

- 自动提交只允许符合成功交付条件且在授权范围内的闭包。
- 取消后产品文件和 index 保持原样；不得顺便回滚、清空或暂存用户修改。
- 取消记录、原因和已有有效证据可以可靠保存；取消不能显示为代码成功交付。
- 如果已有提交，再取消只记录事实，不隐式撤销或重复提交。

必测：各非成功闭包在有未提交修改、有暂存修改、已有提交和无改动时的行为；重复取消幂等；同时检查 HEAD、文件字节、index 和结果摘要。

## 6. R3 与 O1：可恢复收尾，只补未完成动作

**目标：** 已验证、已提交、摘要已保存、归档待处理和资产待入库有可辨认的事实，恢复不误报、不重复副作用，也不无条件重跑全部验证。

实施要求：

1. 先盘点现有 task、操作日志、ledger 和归档回执，选定一个收尾操作权威，复用已有可靠能力。
2. 持久化必要进度，不在不可恢复的窗口提前将任务标成完整终态。代码交付与资产完成可以分开，但 status 必须明确剩余工作。
3. 恢复同时处理正常错误返回、异常、进程终止和系统重启，不能只依赖内存中的异常回滚。
4. 验证已完成且其输入仍相同时直接复用；代码、依赖、验证配置或必要环境变化后重新执行受影响验证。
5. 已提交结果可通过候选身份和 Git 对账确认；提交成功但回执未写时不得创建重复提交。
6. 归档或远端动作结果未知时先检查已有回执与目标状态，再决定重试。
7. `--no-commit` 明确表达工作区交付；之后手工提交再归档仍有受支持的恢复入口。
8. 状态视图只读且快速；错误提示中的“只补归档”等承诺必须与实际命令行为一致。

必测中断点：验证完成后、commit 前后、收尾进度写入前后、归档搬移前后、归档回执前后、资产入队前后。使用至少一项真实子进程终止测试；只注入 Python 异常不足以证明崩溃恢复。

验收需检查：无重复提交、无重复外部副作用、状态真实、可再次恢复、有效证据不无故重跑。模拟外部结果未知时保留未知，不自动改成成功或失败。

## 7. R4：CI 证据绑定实际交付内容

**目标：** CI 证明的内容必须与当前候选产品内容一致，且在门禁和实际使用时仍有效。

- 不能用 `HEAD^{tree}` 代替当前工作区内容。明确 staged、unstaged、untracked、删除、重命名、子模块和平台换行的处理语义。
- 可以使用不修改真实 index 的候选快照，或采用可靠的内容比较；必须与 CI 的内容身份口径一致。
- Harness 状态及明确非产品运行输出可以排除，产品源文件、测试、依赖锁和构建配置不得为方便而排除。
- 导入时与门禁使用时均检查绑定。导入后代码再次变化不能保持有效通过状态。
- 旧收据兼容策略明确；无法证明有效性的收据不能默认为可信。

必测：HEAD 未变但各种工作区改动；导入后再修改；同内容不同 commit；无关运行输出；测试或锁文件变化；CI 实际执行期间改变了候选内容。反例必须在导入或使用边界拒绝，且最终 gate 不得返回可发布的通过结果。

## 8. R5：CI 验证能力、分片与来源可信

**目标：** 收据证明实际执行的检查及其范围，不能靠任意 `--verification` 映射成为全量通过。

1. 明确允许的 workflow/job/step 与验证能力映射，绑定对应策略版本及候选代码；不靠命令文本包含 `test` 判断能力。
2. 收据记录验证类型、平台、完整或部分覆盖、分片身份和预期分片集合。
3. 分片全部属于相同候选、策略与适用的运行身份，且齐全成功，才可聚合成全量结果。缺失、失败、取消、跳过、重复和混合 attempt 均有明确定义。
4. 编译、单元测试、全量测试和平台矩阵不能互相冒充；单个平台结果是否满足要求由项目策略决定。
5. 整体 workflow 是否成功与某项验证是否成功分别记录；不得由一个成功步骤宣称所有必需检查通过。
6. 校验真实来源。自行重算的 JSON 哈希只能证明一致性，repository 字符串也不是来源认证。选择适合项目的可信下载回执、CI API 对账或离线可验证证明；不强制引入重型签名基础设施。
7. 若离线导入无法建立可信来源，只能标为待核验，不能按“已验证的外部证据”放行。网络失败不能转成可信成功。

必测：单分片、完整分片、重复冒充缺失分片、跨 run/attempt 拼接、一个失败分片、成功 echo 步骤、测试步骤冒充 compile、手改后重算哈希、错误来源和未知工作流。保留真实 CI 产出→获取→导入→门禁的正向证据，不能仅靠手工构造 JSON 完成验收。

## 9. O2：完成任务依赖、写入冲突与增量评审

对应 [批次 3 主体](batch3/design-evidence-driven-delivery-2026-09-09.md) 尚缺的任务依赖与增量评审范围。

### 9.1 编排与冲突

- 单任务不强制建立复杂 DAG；有独立工作项时记录实际依赖、写入范围和验收条件。
- 调度前识别相同文件、父子路径、共享配置和接口依赖冲突；依赖缺失或成环明确报错。
- 冲突工作串行化或使用隔离工作区，不允许多个执行者争写后再以最后写入者为准。
- 执行中越过声明边界时停止相关写入并重新协调，不影响独立安全工作。
- 不同工作项各自通过后仍验证实际合并结果；保留低资源并发上限与取消传播。

必测：独立任务可并行；相交范围被阻止或串行；父子路径冲突；依赖阻塞与失败传播；合并造成的新失败；重启后不重复分派已有运行任务。

### 9.2 增量评审

- 评审输入从本轮 diff、受影响接口、调用者、测试与既有未解决发现构建。
- finding carryover 只表示旧结论携带，不能当作增量输入构建已完成。
- 公共 API、依赖、权限和全局配置变化时扩大审查范围；依赖图缺失或不确定时保守回退。
- 继承结论绑定源内容与适用条件；新改动影响旧结论时重新审查。
- 对照完整评审检查漏审，不用上下文减少本身证明质量提升。

必测：无关模块不重审；跨模块调用与接口变化正确扩展；移动文件和行号偏移；已修复发现不重复出现；未解决发现不因局部输入消失；全局配置触发扩大范围。

## 10. O3 与 O4：实际成果摘要与自动资产闭环

### 10.1 摘要内容

每次任务保存：实际完成的行为、代码位置、验证与未验证项、残余风险、必要下一步。目标与已完成成果分字段，禁止直接把 goal 复制成成功说明。

事实由实际 diff、测试及操作回执派生；模型补充动机、取舍与原因。无法证实的解释保留为推测，空白资产不凑数。支持失败、取消、部分完成、工作区交付和正式发布等不同结果。

验收采用至少一例目标与最终结果不同的任务、一个未验证项和一个失败任务；检查摘要没有夸大完成，也没有遗漏用户必须处理的问题。

### 10.2 异步处理与持久性

- 本地可靠保存摘要与必要资产输入后，远端上传、提取和索引在独立队列处理，不拖住本地代码交付。
- 优先复用现有 outbox、回执和重试；不再创建功能重复的队列。
- 无常驻宿主时，在下次启动或显式维护命令继续，状态明确，不承诺不存在的后台执行。
- 队列具备幂等身份、并发领取保护、退避、失败详情和容量策略；磁盘写入失败显示未保存，不静默丢失。
- 保存来源、项目、适用版本、验证状态、替代关系和失效条件。重复合并、冲突待确认、过时标记的行为有测试。
- 不自动改长期规则、安装可执行 Skill 或扩大权限；这些形成提案。
- 区分被检索、被采用与被验证有效。用后续任务实际消费至少一条资产，记录适用和不适用结果。

必测：离线交付、队列重启、重复消费、领取后崩溃、远端成功但本地回执失败、容量不足、冲突知识、敏感内容排除与跨项目隔离。

两仓契约变化需做兼容与真实往返验收。没有远端环境时先完成本地及契约测试，但远端闭环必须保持待验证，不能改为“全部完成”。

## 11. O5：重新建立可信的收益证据

先校正现有试点报告的确定性：保存原始数据和当时版本，将超出证据的“清零”“质量零回退”“全部达成”限定为实际样本范围，不删负结果。

对照原生 Agent、审核基线和新候选版本。至少覆盖说明修改、局部缺陷、普通功能、跨模块改动、高风险变更、中断恢复。冷暖缓存分开，固定需求、起始代码、工具和模型配置，使用独立工作区与新会话防止答案泄漏。

- 每个适用组合至少重复 3 次作为初步试点；样本不足以支持普遍结论，报告不确定性。
- 隐藏验收与实现者分离，包含失败路径、兼容和用户修改保护。
- 记录端到端时间、流程维护时间、失败恢复、人工介入和可采集的 token；不能扣掉产品缺陷造成的成本。
- 新旧版本在一次对照中冻结；发现缺陷需修复时，保留该轮结果，再用新版本重建对应对照。
- 目标沿用原提案：轻任务中位时间下降至少 20%、流程维护下降至少 50%，以质量约束为前提。不得自行降低目标；未达标则继续诊断或明确报告未达标。
- token 或真实长期效果无法采集时标未知，并区分测量工具已实现与收益已验证，禁止用行数或候选数量代替。

资产短期验收要求至少一条经后续任务验证的有用资产与一条被正确拒绝的不适用资产；持续长期收益单列后续观察，不能伪造历史采用。

## 12. O6：内部职责收敛与旧路径退役

先列出任务状态、提交范围、风险策略、执行收据、验证状态、归档回执、摘要和资产队列的写入方、读取方、恢复用途及外部消费者。

- 同一事实一个权威写入方；展示与导出是派生结果。
- CLI 负责参数和序列化，内部业务调用返回结构化结果，不长期通过捕获子命令 stdout 组合业务。
- 合并重复生命周期和执行包装。能复用的旧正确性机制迁入统一路径，不能在外面新增一层后保留所有旧写入路径。
- 新任务只走新权威路径；旧任务按协议版本恢复。只读兼容与双写要明确区分。
- 无消费者且有替代能力的旧步骤、重复产物和代码按审批与兼容规则退役；受真实外部消费者阻塞的项目保留清单和退出条件。
- 不要求改为单一编程语言或拆更多包；评价逻辑变更涉及的模块、重复状态数量、恢复复杂度与日常调用成本。

交付前给出前后对比及逐项保留理由。简单减少 LOC 不算完成解耦；所有旧路径全部保留也不能宣称退役完成。

## 14. 测试、发布与复审交付

启动时核对当前 `package.json`、CI 与测试 runner 的命令和资源规则。基线存在 `npm run check`、`npm run test:harness:safe`、`npm run smoke:pack`；它们覆盖不同内容，不能互相冒充。`npm run check` 不能单独证明全部 Python 场景通过。

使用与改动相称的定向测试，并覆盖 R1～R5/O1～O6 的行为矩阵。完整验证与进程资源管理遵守仓库实际要求，不绕过单实例锁或已有失败检查。必要的高资源检查缺授权时明确列为未验证。

涉及分发时同步 Harness bundle、契约生成物与消费端技能，验证候选打包安装和原始源码行为一致。合并后候选改变则补适用验证。Git 推送、CI 成功与 npm 发布分别记录，不混为一个“已发布”。

满足以下条件才可宣称整个实施完成：所有必做项目已实现并得到相称验证；五个缺陷在新代码上无法复现；故障路径不误报与不丢失；真实 CI 和资产往返已验证；效果目标有证据或被明确判定未达标并继续处理；无用“后续优化”隐藏本次范围。外部前提阻塞时可交付阶段成果，但整体状态必须保持未完成。
