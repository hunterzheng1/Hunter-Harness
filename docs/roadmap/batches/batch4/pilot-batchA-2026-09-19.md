## 8. 关键方法学发现：工作流合规性缺口（本批最重要产出）

盲评与效率数据交叉核验时发现：

1. **全部 9 次 C 组运行均未创建 `.harness/changes/` 回执**（仅存在 init 基础设施文件）；B 组也仅 3/9 次创建（T2-B-r2、T3-B-r1、T3-B-r2）。
2. 直接原因：1.1.0 各阶段 skill 明确「**仅当用户显式调用时使用；不得自动触发**」，而批 A 任务提示仅写「按工作流要求完成任务」，未显式调用任何阶段入口 → C 组运行处于「harness 已安装但未激活」状态，测得的是**安装态上下文成本**而非**工作流执行成本**。
3. 质量闸不覆盖流程合规：任务卡验收与隐藏清单均为产物正确性/边界项，盲评无法也不应发现「未走流程」——三组在该口径下全部公平，但**效率对照因此不同条件**。

**含义**：批 A 的「C vs B 效率大胜」是真实但片面的——它证明 1.1.0 的**投影/上下文体积**大幅缩减，却不能证明**工作流激活态**下的 −20%/−50%。后者恰是 O5 效率证据的核心问题，必须由批 B 修正方法后测量。

## 9. 异常与数据质量备注

- **自提交**：4 次 B 组运行（T1-B-r1/r2/r3、T2-B-r3）自行 `git commit` 了改动（工作树干净、HEAD 前移），导致 `patch.diff` 缺失/为空；盲评不受影响（评审克隆含提交历史），但采集工具链未覆盖 commit 形态产物。
- **包络解析**：0/27 运行取得 numTurns（宿主 headless 会话普遍未落可解析 result 包络；设计已声明该指标弱依赖）。多数运行 1 个 trace pid，少数 0-3 个。
- **极端值**：T1-C-r3（1719s，36 条工作流命令——C 组唯一深度触发流程的运行）、T3-C-r3（3478s，协调耗时 680s）、T1-B-r1（861s，numTurns=256）。单元格内核差最高约 10 倍，n=3 下中位数对极端值敏感。
- **T3-C-r3 盲评批注**（非阻断）：事件 schema 与仓库常见发布判定存在漂移，已记录供后续校准。

## 10. 不确定性声明

- 本批为**试点批**：每格 n=3、单机（Windows 11 + CodeBuddy）、单模型配置；run 内方差大（最高 ~10 倍），全部中位数结论均为初步量级判断，不作统计显著性声明。
- 两组运行失败（timeout / api-error）按设计计入缺口而非剔除重抽。
- token 为含缓存的 totalTokens 合计，跨组公平但非计费口径。

## 11. 对批 B（WI-O5.4）的建议

1. **任务卡提示显式要求执行工作流**（如强制 `harness_task.py begin/finish` 或阶段 skill 调用），否则 1.1.0 按设计不激活，对照无效。
2. **验收清单加入流程回执项**：要求 `.harness/changes/<slug>/`（events/evidence/ledger/execution-log）存在并纳入隐藏检查，由盲评核查流程合规性。
3. **采集工具链覆盖 commit 形态产物**（`git diff base..head`），并修复包络解析以恢复 numTurns。
4. 每格 n 提升至 ≥5，固定模型版本，设置跨 run 冷却（避免 API 抖动与限速）。
5. 仪式写作时间改为人工登记（每 run 后记录），补全流程维护口径。
6. 重点复核 T1-C-r3 / T3-C-r3 两次 C 组深度触发运行，作为「激活态成本」的先行参考点（T1：~28.6min/36 条；T3：~58min/680s 协调）。
