## 3. 关键发现

### 3.1 P12 第二数据点：跨模块 artifact-protocol 邻接未升档

任务定义风险档位标注 standard，备注「涉及 artifact-protocol 邻接，若
classify 升档按升档后流程执行——这本身是测量点」。实测：**未升档**。

- diff 路径：`harness/scripts/harness_change.py`、
  `harness/scripts/tests/test_harness_change.py`、
  `packages/cli/src/commands/sync.ts`、
  `packages/cli/test/sync-process.test.ts`
- 逐 marker 核对（harness_gate.py:1502-1510）：artifact/protocol/manifest/
  baseline/state//shared/workflow-policy 均无路径交集 → signals=
  ['production-code'] → standard

与 T5（schema 变更漏判 full）同根因：**路径启发式识别不了「变更的是状态
输出契约」语义**——本任务改的正是 harness_change.py status 的输出 schema
（Python↔TS 的线上契约），但路径上没有任何 full marker。两个数据点合并
结论：P12 不是孤例，是路径启发式的系统性盲区；「风险升级有效性」在
批次 1 的两个测量点（T4/T5）均未达成（正确档位任务不受影响，但该升档
的不升档）。

### 3.2 任务规格的 snake_case 误导（P8 同类，实现者已绕开）

T4 规格说「保持 snake_case 线上契约（如已有 camelCase 投影则补投影）」。
实际线上契约是 camelCase（`changeId`、`reasonCodes`、T3 定义的
`lastActivityAt`）；Python 侧输出也是 camelCase。实现者正确识别了括号里的
让步条款（「如已有 camelCase 投影则补投影」），选择 camelCase 透传 +
类型断言不重命名键（round-trip 测试显式断言无 `last_activity_at` 键）。
规格主句与实际契约相反——任务设计侧的规格漂移，与 g2/g3 T3 的 P8
（createdAt vs timestamp）同模式。

### 3.3 主仓 Python 侧缺字段的发现

T4 规格假设 T3 已交付（「把 T3 的 lastActivityAt 字段透传」），但 T3 是
试点克隆、从未合入主仓——主仓 `harness_change.py` status 输出根本没有
`lastActivityAt`。验收条件 1（三处一致）迫使实现者发现此缺口并最小化
补齐 Python 侧（helper + 字段 + 3 个回归测试），而非只改 TS。任务链的
隐式依赖（T4 依赖 T3 交付物）在试点方法学下不成立——采集记录需注明
本运行的 Python 侧改动等价于重做 T3。

### 3.4 vitest cwd 陷阱（试点方法学）

契约测试通过 `runProcess` 直接 spawn Python：vitest 的 `process.cwd()` 是
repo root（非 packages/cli），脚本相对路径按 `../../harness/...` 拼接会
解析到仓库外（`E:\MyProject\AI Related\harness\...`），Python 退出码 2
（can't open file）且 stderr 为空难定位。修复：按 repo root 拼
`harness/scripts/...`。后续跨语言契约测试需注意 vitest cwd 语义。
