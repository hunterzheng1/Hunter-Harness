## 3. 关键发现

### 3.1 P14：恢复 = 全量重验，无证据复用

T6 验收条件 1「不重跑已通过的验证」**未达成**：`_run_verification`
（harness_task.py:763-827）总是执行命令，无 can-reuse/ledger 复用检查。
中断后恢复的成本 = 完整验证成本（本样本 213 s，其中 npm 链 207 s 重复
执行）。

- **影响**：恢复路径正确性无虞（幂等副作用 + 覆盖式 ledger），但成本
  效率损失——中断一次多付一轮全量验证。对照：harness_ledger 自身有
  can-reuse 机制（tests_executed/tests_reused_from 字段），轻任务入口
  未接入。
- **权衡**：接入复用需校验输入集哈希未变（中断后 diff 未动才可复用），
  复杂度中等；轻任务定位是短平快，全量重验的简单性 vs 复用的节省，
  需产品决策。批次 1 记录为候选方案改进点，非阻断。
- **规格偏差说明**：T6 规格假设的恢复机制（`PHASE_CLOSE_RESUMED` 或
  等价物）在轻任务架构中不存在——轻任务的等价语义是「task.json open
  即可重跑」，恢复机制极简但无增量续跑。

### 3.2 中断副作用足迹为零（验证阶段）

验证执行中的中断不留下任何需要清理的状态：无事件、无 ledger、无收据；
gate-policy.json/risk-classification.json 被下次运行幂等重写。恢复操作
就是「重跑同一条命令」，无任何状态修复步骤。这满足 T6 验收条件 2 的
精神（无重复副作用）——因为中断点根本没有副作用落盘。

### 3.3 后台进程管理陷阱（试点方法学）

- Git Bash `$!` 返回 bash 内部 pid，`taskkill //PID` 找不到（需 `ps -W`
  映射 winpid，且 python 进程名匹配不稳定）
- `(cmd &)` 分离子 shell 的进程在工具调用结束后被回收——跨工具调用的
  后台任务必须用 run_in_background
- kill 窗口 < 10 s 时，「检测 → 找 pid → kill」的工具调用链延迟（秒级）
  会错过窗口；需单工具调用内完成 launch-poll-kill 闭环
