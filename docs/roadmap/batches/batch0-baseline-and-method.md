# 批次 0：任务成本基线与对照方法

> 日期：2026-09-07
>
> 状态：已确认的产品决策与基线方法；任务集与度量映射为可执行契约，首次实测数据待采集。
>
> 依据：[产品优化提案（../proposals/product-optimization-proposal-2026-09.md）§9（如何证明更好）、§10（批次 0）。
> 本文档不修改任何运行逻辑；它定义批次 0 的交付物与验收口径。

## 1. 已敲定的产品决策（2026-09-07）

| 决策 | 结论 | 对批次 0 的直接影响 |
|---|---|---|
| 首要用户 | 个人与小团队优先 | 任务集取材于个人/小团队日常开发；治理类任务（共享权限、组织审计）不进入首批任务集 |
| 资产自动化 | 事实+经验自动保存；规则与可执行资产受控 | 资产维度只度量事实/经验类沉淀的质量与采用，不度量规则自动生效 |
| 阶段体验 | 新任务默认完整任务入口，保留显式阶段调用 | 对照实验的「候选方案」= 完整任务入口形态；「现状」= 固定阶段 Skill 串行调用 |

## 2. 代表任务集（§9.1）

六类任务，每类一个具体任务，固定起始代码与验收要求。目标仓库取 Hunter-Harness
自身（dogfooding，个人/小团队画像的真实项目）；起始 commit 在任务定义中钉死，
每次实验用独立工作区（fresh clone 或 worktree），避免上一轮答案与知识泄漏。

| # | 类型 | 任务 | 起始状态 | 验收要求（对实现者可见） | 风险档位 |
|---|---|---|---|---|---|
| T1 | 文档修改 | 修正 `harness/harness-execute/SKILL.md` 中一处过时描述（指定段落，验收时给出正确内容） | 固定 commit 的干净树 | diff 仅触及指定段落；文档契约测试通过 | fast |
| T2 | 局部缺陷修复 | 修复一个已知可复现缺陷（预先在任务定义中给出复现步骤与期望行为） | 固定 commit + 复现脚本 | 回归测试证明缺陷已修；无行为外溢 | fast/standard |
| T3 | 普通功能 | 为 `harness_change.py status` 输出增加一个汇总字段（指定字段名与语义） | 固定 commit | 新字段出现且语义正确；既有 42 测试全绿 | standard |
| T4 | 跨模块变更 | CLI 与 Python 脚本之间传递一个新字段（两端 + 契约测试） | 固定 commit | 三处（py/TS/test）一致；类型检查与聚焦测试绿 | standard |
| T5 | 迁移/权限变更 | 修改一个状态文件的 schema 并提供兼容读取（指定旧→新映射） | 固定 commit + 旧 fixture | 旧 fixture 可读、新写入符合新 schema；迁移测试含旧/新双 fixture | full |
| T6 | 中断恢复 | 在 T3 执行中途中断（指定中断点：execute 关门前 kill），验证恢复 | T3 的中间状态快照 | 恢复后不重跑已验证步骤；状态一致；无重复副作用 | standard |

**任务定义的固定要素**（每个任务一份，存于本目录 `batch0/tasks/T*.md`）：
起始 commit hash、需求原文（中文）、验收条件（可判定）、禁止事项、超时预算。

**独立验收保留项**（§9.1：不提供给实现者）：每任务另备 2～3 个行为测试/风险场景，
由评估侧在交付后运行；「当前测试都过了」不单独证明质量。

## 3. 对照组

三组固定起始代码、需求、模型配置、依赖环境与验收要求：

1. **原生 Agent**：不加载任何 Harness Skill，直接给需求。
2. **当前 Harness**：现状固定阶段流程（plan → execute → archive，按 classify 档位）。
3. **候选方案**：完整任务入口（批次 1 交付后加入；批次 0 阶段先跑组 1/2 建立基线）。

冷缓存（新会话、无知识命中）与热缓存（同会话第二个任务）分开统计。
先用小样本（每任务每组 2～3 次）排除明显退步，再扩大。

## 4. 度量映射（§9.2 → 现有采集能力）

| 维度 | 指标 | 现有采集 | 缺口 |
|---|---|---|---|
| 结果 | 验收通过、严重缺陷、遗漏需求、返工 | 无自动采集 | 评估侧人工判定 + 独立验收测试结果 |
| 时间 | 端到端墙钟、模型工作、工具执行、**流程维护**、人工等待 | `harness_efficiency.py`：wallClock/activeTime/resourceWait、timingByStage | 流程维护时间需从 timingByStage 中按阶段拆出协调段（bootstrap/configure/handoff/gate 仪式）vs 验证段；原生组无 Harness 事件，需会话级计时 |
| 成本 | token 与费用 | 无自动采集 | 不可采集时标「未知」，不用文件行数代替（§9.2 原文） |
| 摩擦 | 人工介入、重复澄清、参数错误、状态修复次数 | `manualWrapperCount`、`repeatedCommandsWithoutNewEvidence` | 人工介入次数需评估侧记录 |
| 编排 | 等待依赖、重复探索、合并冲突、并行节省 | 无自动采集 | 首批任务集无并行编排场景，记 N/A |
| 验证 | 无新证据重跑、测试漏选、错误证据复用 | `repeatedCommandsWithoutNewEvidence`、invalidationReasons（E1 已接通）、failureClasses | 测试漏选需对照受影响测试清单人工判定 |
| 资产 | 摘要准确性、无依据条目、重复冲突、实际采用 | 知识候选生成（确定性，含未裁决警告） | 「实际采用」需后续任务追踪，批次 0 只记录候选数与质量抽查 |
| 维护 | 权威写入点数、协议变更涉及模块数、重复实现 | 状态与消费者清单（见 §5） | 已有；随批次 5 收敛复测 |

**流程维护时间的操作定义**（§9.2）：身份、格式、阶段交接和状态修复等协调开销。
具体口径：Harness 组 = bootstrap/configure-plan/prepare/begin/gate begin/gate close/
resolve/archive execute 等协调命令的累计时长 + 模型手工写仪式产物（test-report、
echo 报告）的时长；验证命令（test_runner exec、ledger record）不计入。原生组 = 0
（无流程），其总时间差即流程税的直观对照。

## 6. 首次实测的执行计划

1. 建任务定义文件（`batch0/tasks/T1-T6.md`，含钉死的 commit 与验收）。
2. 每任务准备独立工作区（worktree 或 fresh clone）。
3. 先跑组 2（当前 Harness）T1/T3 各 2 次，验证度量采集链路走得通
   （效率统计落 summary-data、评估侧记录表可复用）。
4. 跑组 1（原生 Agent）同任务同次数。
5. 汇总首份基线数据：按 §4 口径填表，标注样本量与不确定性。
6. 试点门槛（§9.3 候选目标，非承诺）：低风险样本端到端中位时间降 ≥20%、
   流程维护时间降 ≥50%；质量硬约束零回退（无新严重验收失败、无用户修改丢失、
   无重复外部副作用）。

## 8. 不做什么

- 不先实现通用框架或完整任务入口（批次 1 起按基线数据决定形态）。
- 不修改现有 Skill/脚本行为（本批次纯观测与定义）。
- 不用文件行数、知识条目数等代理指标冒充成本或资产质量。
